# Worker URL → existing Pi → OpenAI screen (not connected)

Scope: review 5557187580 on ops#563. This is the screen-only alternative, not completed sign-in, ChatGPT plan use, or deployed conversation support.

`/` or `/auth` shows an explicit warning and a POST form. `/auth/start` invokes the unchanged installed Pi OAuth `login`; Pi generates state, nonce and S256 PKCE. The app rejects the manual-code prompt, waits for Pi's own cleanup, then returns its exact authorization URL as a non-cacheable 303. No callback/code is accepted. Retrying creates fresh authorization state while reusing the host identity. SDK errors/URLs are never echoed.

`package-screen.py` packages the same Vite-built app /auth handler behind a screen-only entry. The provided Wrangler config has no DO, static asset, credential, callback or chat bindings. It disables preview URLs and Worker observability. The original app keeps its conversation tests; the screen-only entry cannot dispatch those routes. This is an alternative deployment entry, not an additional always-on bridge.

The `pi-worker-screen-<head>` CI artifact contains the actual JS modules, Wrangler config and source identity. Root selects the approved destination/name and supplies the non-secret `PI_OAUTH_HOST_ID` (one UUID per Worker host, reused across retries). Missing/invalid identity returns a generic 503 and retry UI. Do not supply PI_CHATGPT_BOOTSTRAP, API keys or OAuth credentials to this screen-only deployment. Do not deploy the original chat config as this slice.

The producer runs on the candidate branch and on canonical `proposals` pushes that change its declared inputs. After ops#563 merges, the envs deployment consumes the successful screen artifact for that PR's actual merge commit. The proof and deployment artifacts come from the same build; the workflow itself has no deployment credentials or authority. The canonical destination is the existing `pi` Worker. The full mock app and its DO configuration remain outside this screen artifact's admission scope.

The existing protected envs/dev-projection deployment path belongs to root; this PR does not write its secrets, account settings, Access, branch permissions, live Worker or deployment. The account locator is already known to root and must not be asked again. Root must protect the selected hostname and all reachable entries and read back the exact deployed version. Worker-level Access does not support the full app's WebSockets; that later app needs the appropriate hostname-based Access configuration. Do not reuse the existing SSH-only Access policy as proof of Pi owner protection.

CI performs workerd tests plus real loopback HTTP against the packaged Worker. A new empty browser profile attempts the actual OpenAI screen without clicking an account or consenting; callback/token paths and external POSTs are blocked. `screen-browser.json` reports AUTH_SCREEN_VISIBLE or AUTH_SCREEN_NOT_PROVEN honestly. An external anti-bot/network failure is not a completed screen proof and must be resolved/read back by root at the protected deployed URL. No OAuth query, user cookies, personal screenshot or credential belongs in public evidence. The optional screenshot is taken only in CI's new account-free browser context.

The full target still needs separately established provider-compliant credential handling/persistence, consent, access protection, authorized real inference/refresh and deployed DO continuation. Neither this screen nor prior mock Green establishes those conditions. Never add a replacement OAuth protocol or claim live success from the screen.

As checked on 2026-10-18, [Sign in with ChatGPT Terms, dated 2026-09-29, sections 1–2](https://openai.com/policies/sign-in-with-chatgpt-terms/) define Authentication Tokens as access and refresh tokens and require persistent storage to be local and under the user's control, excluding remote or managed environments. The [technical self-hosted runtime documentation](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) does not establish an exception to that requirement for Cloudflare Workers or Durable Objects. Do not put real SIWC access or refresh tokens into the experiment's DO bootstrap/storage without an explicit applicable provider basis. Its remote credential persistence and rotation tests use synthetic credentials only. User consent and an encrypted store do not by themselves supply that provider basis.
